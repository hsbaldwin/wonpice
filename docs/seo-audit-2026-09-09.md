# 프로젝트 전역 SEO 평가·검증

검증일: 2026-09-09 KST. 대상: [운영 사이트](https://curtain.wonpice.com/) 및 로컬 프로덕션 빌드. 소스 기준: `07deea9`, Next.js `16.3.4`.

**판정: 기술 SEO의 기본 구조는 양호하다. 현재 운영 사이트는 검색 공개 전 상태이며, 공개 전에 콘텐츠 안내·Breadcrumb·공유 메타데이터를 보완하는 것이 좋다.** 이번 작업은 평가와 검증이며, 아래 발견사항을 수정하거나 검색 공개 설정을 변경하지 않았다.

사용자가 설명한 “검색엔진 노출 전” 상태와 실제 응답이 일치한다. 이를 구현 결함으로 분류하지 않았다. `SITE_INDEXABLE`을 읽는 [사이트 설정](/Users/studio/Desktop/Curtain/lib/site.ts:7), [robots 생성](/Users/studio/Desktop/Curtain/app/robots.ts:5), [사이트맵 생성](/Users/studio/Desktop/Curtain/app/sitemap.ts:6)이 같은 정책을 사용한다.

## 2. 확인된 보완사항

### P2 · `/guides`, `/about`의 Breadcrumb 항목 부족

운영 HTML에서 두 페이지의 `BreadcrumbList.itemListElement`가 각각 1개다. JSON 문법은 정상이지만 Google의 Breadcrumb 표시 요건은 **최소 2개의 ListItem**이다. 나머지 카테고리는 2개, 포스트는 3개로 이 조건을 충족한다. [Google Breadcrumb 요건](https://developers.google.com/search/docs/appearance/structured-data/breadcrumb#structured-data-type-definitions)

- 근거: [공통 구조화 데이터](/Users/studio/Desktop/Curtain/components/guide-ui.tsx:58), [가이드 허브](/Users/studio/Desktop/Curtain/app/guides/page.tsx:73), [서비스 소개](/Users/studio/Desktop/Curtain/app/about/page.tsx:89).
- 영향: 두 페이지의 Breadcrumb 검색 표시 요건 미충족. 페이지 자체가 색인될 수 없다는 의미는 아니다.
- 수정 방향: 화면의 경로와 JSON-LD에 `홈 → 커튼 가이드`, `홈 → 서비스 소개`를 함께 반영하거나, 단일 항목일 때 Breadcrumb 구조화 데이터 생성을 생략한다.
- 완료 기준: 해당 두 페이지에서 실제 사용자 경로와 일치하는 2개 이상의 항목·연속 position·유효 URL을 확인한다.

- 현재 [도우미 첫 화면](/Users/studio/Desktop/Curtain/components/quote-helper.tsx:423)과 [마지막 버튼](/Users/studio/Desktop/Curtain/components/quote-helper.tsx:685)에는 실제 제공되는 흐름이 구현돼 있다.

검색 방문자가 읽은 내용대로 행동할 수 없어 콘텐츠의 정확성과 전환에 영향을 준다. 기능을 복원하는 방향을 임의로 정하기보다, 현재 화면에 맞춰 “치수 입력 → 필요한 기능 선택 → 저장된 내용 확인·견적 문의”로 안내를 일치시키는 것이 적절하다. 소스 파일이나 테스트에 PDF 관련 코드가 남아 있는 사실만으로 공개 기능이 있다고 판단하지 않았다.

### P2 · 페이지별 Twitter 정보가 공통 문구로 고정되고 OG 필드가 누락

운영 응답에서 다음을 확인했다.

| 필드                                   | 확인 결과                                   |
| -------------------------------------- | ------------------------------------------- |
| `twitter:title`, `twitter:description` | 17페이지 모두 홈의 동일 문구                |
| 홈 `og:url`                            | 없음                                        |

원인은 [루트 metadata](/Users/studio/Desktop/Curtain/app/layout.tsx:28)의 공통 Twitter 값과 [하위 페이지 openGraph 객체](/Users/studio/Desktop/Curtain/app/guides/[category]/page.tsx:31)의 재정의다. 설치된 Next.js 가이드에서도 중첩 metadata는 깊게 병합되지 않고 마지막 객체로 교체된다고 명시한다. [로컬 Next.js 문서](/Users/studio/Desktop/Curtain/node_modules/next/dist/docs/01-app/03-api-reference/04-functions/generate-metadata.md:1344)

이는 HTML title·description의 중복 문제가 아니다. 그 두 필드는 17페이지 모두 고유하다. 공유 카드에서 글의 주제를 구별하기 어렵고 일부 소비자가 공통 정보를 받지 못하는 문제다. 공통 메타데이터 생성 함수를 두고 페이지별 제목·설명·URL·타입을 명시하는 방식이 적합하다. [네이버 콘텐츠·공유 메타데이터 안내](https://searchadvisor.naver.com/guide/markup-content)

### P2 · 현재 SEO 테스트만으로 검색 공개 준비를 판정하기 어려움

기존 테스트는 이번에 통과했지만 위 문제를 검출하지 못한다.

- [HTTP 검사 경로 목록](/Users/studio/Desktop/Curtain/tests/seo-http.test.ts:16)은 16페이지이며 `/about`이 빠져 있다.
- title·description의 실제 DOM 값과 고유성, robots 메타·HTTP 헤더, 공개 사이트맵과 실제 페이지의 일치를 검사하지 않는다.
- JSON-LD는 문자열 존재 확인에 머물러, 파싱·Breadcrumb 항목 수·canonical 일치 여부를 검증하지 않는다.
- [공개 설정 테스트](/Users/studio/Desktop/Curtain/tests/seo-publication.test.ts:44)는 공개/비공개 모듈을 별도 프로세스에서 검사하지만, 실제 공개 서버의 전체 SEO 응답 검사와는 다르다.

이번 감사에서는 이 범위를 별도 전수 검사로 보완했다. 향후 배포 검증에 `/about`, HTTP robots·사이트맵, JSON 파싱과 유형별 최소 요건, 공유 메타데이터를 추가하면 회귀를 줄일 수 있다. 공개·비공개 모드의 기대값을 나누어 정상적인 미공개 상태가 실패로 처리되지 않도록 해야 한다.

## 5. 모바일·렌더링 측정

운영 URL을 새 Chromium 컨텍스트에서 페이지별 3회 측정했다. 화면은 390×844, 캐시는 비활성화했고 CDP로 다운로드 1.6Mbps·업로드 0.75Mbps·지연 150ms·CPU 4배 감속을 적용했다. 페이지 load 후 2.5초까지 관찰했다. 이는 Lighthouse 점수나 실제 휴대전화 측정이 아닌 브라우저 실험값이다.

| 페이지      | LCP 3회                 | LCP 중앙값 | CLS     | load 이벤트 중앙값 |
| ----------- | ----------------------- | ---------- | ------- | ------------------ |
| 홈          | 1.200 / 0.884 / 0.772초 | 0.884초    | 0.00083 | 15.97초            |
| 실측 가이드 | 0.716 / 0.760 / 0.728초 | 0.728초    | 0.00060 | 8.91초             |

LCP 대상은 두 페이지 모두 H1이며 첫 본문 표시는 양호하다. 다만 전체 자원의 다운로드가 끝나는 시점은 훨씬 늦다. 실제 WOFF2 다운로드는 홈에서 15.5~16.0초, 실측 가이드에서 약 8.7초 걸렸다. `font-display: swap`으로 대체 글꼴이 먼저 표시되므로 이 다운로드 지연이 그대로 LCP에 반영되지는 않는다. 글꼴 전송량 감소는 여전히 유효한 개선이다.

6회 모두 JavaScript 런타임 오류와 가로 넘침이 없었다. 추가로 홈·허브·실측 가이드를 JavaScript 비활성 상태에서 390×844, 1440×900으로 열었다. 총 6개 조합에서 본문·링크·H1이 존재하고 가로 넘침이 없었다. 도우미 입력 자체는 JavaScript가 필요하다.

Google의 권고 LCP 2.5초·CLS 0.1과 비교하면 이 제한된 표본은 양호하다. 그러나 실제 사용자 75백분위 성능, INP, 재방문·다른 기기·회선 상황을 대표하지 않으므로 **Core Web Vitals 전체 통과로 판정하지 않는다.** [Google Core Web Vitals 설명](https://developers.google.com/search/docs/appearance/core-web-vitals)

## 6. 검색 공개 시 적용할 순서

1. 위 P2 항목 중 콘텐츠 안내·Breadcrumb·공유 메타데이터를 수정하고 실제 HTML로 재검증한다.
2. 운영 환경에서 `NEXT_PUBLIC_SITE_URL=https://curtain.wonpice.com`을 유지하고, 공개하기로 결정한 시점에만 `SITE_INDEXABLE=true`로 재빌드·재배포한다. Preview는 계속 false로 둔다.
3. 운영 17페이지에서 noindex가 제거됐는지, robots가 공개 경로를 허용하는지, 사이트맵에 17개의 canonical URL만 있는지 확인한다. 비공개·관리자·API·제휴 이동 경로는 사이트맵에 포함하지 않는다.
4. Search Console·네이버 서치어드바이저의 실제 소유 확인 및 등록 상태를 확인하고 사이트맵을 제출한다. 소유권 확인 태그가 코드에 없다는 사실만으로 미등록이라고 판단할 수는 없다.
5. 공개 후 URL 검사, Google Rich Results Test, 수집·색인 결과를 확인한다. 이후 실제 검색어·클릭률·방문자 성능 자료로 개선 우선순위를 조정한다.

공개 설정 테스트에서는 `SITE_INDEXABLE=true`일 때 공개 사이트맵 URL 17개, false일 때 0개를 확인했다. 이번 작업에서 운영 공개 설정을 바꿔 검증한 것은 아니다. 네이버의 사이트맵 등록·소유 확인 절차는 [공식 안내](https://searchadvisor.naver.com/guide/seo-basic-intro)를 참고한다.
